# winget packaging

`manifests/` mirrors the layout of [microsoft/winget-pkgs](https://github.com/microsoft/winget-pkgs):
`manifests/d/Devigami/SS14AutoJoin/<version>/` holds the three manifest files for one release, generated by
`tools/make_winget_manifest.py <version> <sha256 of SS14AutoJoin-<version>-windows-x64.exe> [release date]`.

The package is `Devigami.SS14AutoJoin`, a *portable* installer: winget copies the window executable into its
portable folder and adds the alias `SS14AutoJoin` (the first `Commands` entry; `PortableCommandAlias` applies
only to files inside archives) to the path.

Installing this way avoids the SmartScreen prompt. winget does mark the file it downloads, as coming from
the internet zone, but once the hash matches the manifest and the source is a trusted one (the community
`winget` source is), it re-marks the file as trusted zone, which SmartScreen's first-run check ignores.
Read from `microsoft/winget-cli` at `d9acda8` (client 1.31): `UpdateInstallerFileMotwIfApplicable` and the
hash check above it in `src/AppInstallerCLICore/Workflows/DownloadFlow.cpp`. Not yet run on Windows from the
community source. A `winget install --manifest <folder>` of local files is not a trusted source: it takes the
other branch, an attachment scan that leaves the internet-zone mark, so it is not evidence either way.
winget does not sign anything: a browser download of the same file still warns, and policies that demand a
signature still refuse it.

The manifest pins the SHA-256 of the release asset. Never replace or re-sign an asset of a version that is
already in winget, or every install of that version fails its hash check; signing starts with a new version.

## First submission (once, by hand; done for 1.0.0, merged as PR 441430 in 2026-11)

1. Fork `microsoft/winget-pkgs`, copy `manifests/d/Devigami/SS14AutoJoin/1.0.0/` into the same path in the
   fork, and open a pull request. Optionally validate first on Windows with
   `winget validate --manifest manifests/d/Devigami/SS14AutoJoin/1.0.0` and
   `winget install --manifest manifests/d/Devigami/SS14AutoJoin/1.0.0`.
2. The winget bots check the URL, the hash and the schema; a moderator merges. Expect a few days.

## If the bot says the manifest version is deprecated

`winget-pkgs` retires manifest schema versions while a pull request waits (the 1.0.0 submission sat for five
weeks and was then told "This manifest version has been depreciated. Please use version 1.28.0", label
`Manifest-Version-Deprecated`). Nothing about the package changes; only the declared schema does:

1. Set `SCHEMA` in `tools/make_winget_manifest.py` to the version the bot named (the current list is the
   folder names under `doc/manifest/schema/` in `microsoft/winget-pkgs`), regenerate with the same version,
   hash and release date, and run the tests.
2. In the fork, on the pull request's branch, change the two schema lines of each of the three files
   (the `# yaml-language-server` comment and `ManifestVersion`) to the same version. The GitHub web editor on
   the pull request's "Files changed" tab is enough; pushing to that branch updates the open pull request.
   Do not open a second pull request: duplicates are closed.
3. The bots re-run validation on the new commit and clear `Needs-Author-Feedback`; a moderator then merges.

If validation then fails with `SchemaHeaderManifestVersionMismatch` and `SchemaHeaderUrlPatternMismatch`
for each file, the comment line was left behind: winget-cli (`ManifestSchemaValidation.cpp`) reads the
version out of the header URL, compares it with `ManifestVersion`, and compares the whole URL with the
schema's `$id` (case-insensitively, so `defaultLocale` and `defaultlocale` both pass). Both lines must say
the new version; a `# Created using wingetcreate` line above them is fine.

## Later versions (automatic)

`release.yml` has a `winget` job that runs `vedantmgoyal9/winget-releaser` after each release. It reads the
new release's assets, computes the hash, and opens the update pull request in `winget-pkgs` itself. Two
repository settings (Settings, Secrets and variables, Actions) make it work:

* Secret `WINGET_TOKEN`: a classic personal access token with the `public_repo` scope, belonging to an
  account that has a fork of `winget-pkgs`. The job is skipped while the secret is absent.
* Variable `WINGET_FORK_USER`: the name of that account. The action pushes its branch to
  `<fork-user>/winget-pkgs` and by default assumes the owner of *this* repository (`fork-user` in the
  action's `action.yml`, read at tag `v2`), which is wrong whenever the fork sits under a personal account
  and this repository under an organisation. Without the variable the job fails after the release is
  already published; the release itself is unaffected and the submission can then be made by hand.

The update pull request still waits for the winget reviewers, so a version reaches `winget upgrade` some days
after its release.
